# v2.5.432 背包／倉庫索引快取優化

## 範圍
本版延續 v2.5.431 第一階段，不改動玩家資料格式，只降低重複切換分類、搜尋與排序時的 CPU 工作量。

## 背包索引
- 使用 WeakMap 以 inventory 陣列作為鍵，建立已知道具清單、分類數量、子分類數量及頭飾存在旗標。
- 分類／子分類／快速篩選／搜尋／排序結果加入每個 inventory 最多 48 組的有限快取。
- 快取不會持有額外的永久玩家資料；當 inventory 陣列失去引用時，WeakMap 可隨 GC 回收。
- 透過 `invalidateInventoryViewCache(owner)` 在背包變更時刪除對應索引。

## 失效時機
- `addItem`、`removeItem`。
- 個體裝備存入／領出倉庫、穿脫裝備、打洞拆出個體裝備、拆卡銷毀裝備、出售個體裝備。
- 倉庫儲存／匯入時，倉庫清單索引同步失效。
- 讀檔／資料遷移替換 inventory 陣列時，舊快取以舊陣列為鍵，不會被新陣列使用。

## 倉庫解析快取
- 以 localStorage 原始 JSON 字串作為版本識別。
- 字串未變更時重用已解析物件；字串被其他匯入流程修改時自動重新解析。
- `saveWarehouse` 更新快取物件及原始字串，並同步使倉庫索引失效。
- 倉庫近期使用排序仍在每次呈現時對複本排序，確保排序順序不會因快取而過期。

## 保留項目
- 不合併不同 instanceId 的個體裝備。
- 不改變道具 qty、鎖定、自動販賣、卡片插槽、精煉或裝備比較資料。
- 不修改存檔結構或玩家存檔內容。
- 快取只屬於執行階段，不寫入 localStorage。

## 測試
見 `tools/v2_5_432_inventory_cache_regression.js`。

## 合成資料微基準（Node.js）
- 測試清單：20,000 筆道具列。
- 首次建立分類索引：約 63.33 ms。
- 相同篩選條件重複查詢 300 次（快取命中）：約 35.39 ms。
- 每次重新掃描、篩選、排序 300 次：約 1,196.06 ms。
- 此 Node.js 合成測試約快 33.8 倍；只代表索引／篩選核心函式，不等同 Android 實機 DOM、圖片載入或完整 UI 的實測效能。
